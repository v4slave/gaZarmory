# Технический аудит

Дата среза: 2026-09-10. Аудит основан на текущем рабочем дереве, локальных dependency-проверках, тестах, production-сборке и ручном просмотре конфигурации и критических путей. Это не заменяет внешний pentest и нагрузочное тестирование на production-подобных данных.

## Резюме

- критических или высоких уязвимостей в рассмотренном коде не обнаружено;
- `composer audit --locked` и `npm audit` для обоих npm lock-файлов не нашли известных advisory;
- секреты не отслеживаются через `.env`; локальный поиск типовых ключей в tracked-файлах ничего не нашёл, а CI содержит Gitleaks scan полной истории;
- финансовые операции используют транзакции и блокировки, права проверяются на backend;
- главные риски — ресурсоёмкая синхронная обработка изображений, долговечная remembered-сессия и рост стоимости полнотекстовых/аналитических запросов;
- production-сборка проходит, но автоматические тесты сейчас не зелёные: 4 backend-регрессии и 2 frontend i18n coverage-регрессии.

## Что уже защищено

- stateful Sanctum API, CSRF, ограниченный одним origin CORS и `HttpOnly` cookie;
- зашифрованные Discord access/refresh tokens и исключение токенов из JSON;
- Policies/Gates и повторные проверки финансовых команд на backend;
- `DB::transaction()`, `SELECT ... FOR UPDATE` и PostgreSQL advisory lock для конкурентных изменений;
- allowlist сортировок/enum-параметров и parameter binding в SQL;
- лимиты размера и MIME для загрузок;
- Nginx CSP, запрет framing, `nosniff`, ограничение API/OAuth и закрытая раздача private media через `X-Accel-Redirect`;
- очередь с `after_commit`, таймауты внешних HTTP и дочерних процессов;
- доменные индексы для аукционов, начислений, выплат, уведомлений и медиареакций.

## Риски безопасности

### S1 · Средний · CPU/RAM DoS через изображения

OCR и удаление фона ограничивают размер файла, но не ширину, высоту и общее число пикселей. Сжатое изображение с очень большими размерами может дорого декодироваться в GD/Python; OCR дополнительно делает несколько масштабирований и полнопиксельных проходов. Обработка идёт синхронно в HTTP worker. Для preview есть throttle `3/min`, для OCR действует только общий API limit.

Рекомендации:

1. До декодирования проверять `getimagesize()`, максимум стороны и пикселей, например 4096 px и 16 MP.
2. Ввести отдельный per-user throttle и не более одной параллельной OCR/rembg-задачи на пользователя.
3. Перенести тяжёлую обработку в отдельную очередь/worker с memory/CPU limit; для PHP-FPM задать `request_terminate_timeout`.
4. Добавить тесты на чрезмерные dimensions и конкурентные запросы.

### S2 · Средний · долговечная remembered-сессия

После каждого Discord login вызывается `Auth::login($user, true)`. Remember cookie сохраняет вход между перезапусками браузера и увеличивает окно использования украденной cookie; пользователь не может увидеть или отозвать отдельные устройства.

Рекомендации: сделать remember-login явной настройкой, ограничить срок, добавить отзыв всех сессий и документировать реакцию на компрометацию Discord/браузера. Для чувствительных финансовых действий можно потребовать недавнюю повторную аутентификацию.

### S3 · Низкий · публичный cache proxy `archa.ge`

Публичные image endpoints принимают произвольный числовой ID и кэшируют успешный ответ на сутки без проверки `Content-Type` и размера тела. Ограничение `120/min` снижает риск, но не исключает заполнение file cache и загрузку PHP workers ответами upstream.

Рекомендации: проверить JPEG magic/MIME и максимальный размер, добавить negative cache, ограничить диапазон/источник ID, уменьшить отдельный throttle и наблюдать размер cache.

### S4 · Низкий · внешние direct media URL

Для прямых изображений и видео разрешён любой HTTPS-host. Сервер их не загружает, поэтому классического SSRF нет, но браузер участника обращается к адресу автора публикации и раскрывает IP/метаданные запроса. CSP также разрешает `img-src` и `media-src` для любого HTTPS.

Рекомендации: разрешить только доверенные media-hosts либо проксировать контент через проверяющий сервис; как минимум показывать внешний источник и применять строгий `Referrer-Policy` к media elements.

### Операционные замечания

- TLS verification для `archa.ge` выключается только при `APP_ENV=local`. Ошибочная публикация с `APP_ENV=local` ослабит канал; deployment smoke test должен проверять `APP_ENV=production`.
- HSTS намеренно не включён в базовый snippet. Его следует добавить после завершения HTTPS-настройки и проверки всех поддоменов.
- Исторический Gitleaks scan настроен в CI, но локально в этом срезе не запускался: бинарник отсутствует.

### Q1 · Контракт ролей readiness расходится

Backend разрешает readiness всем `canManageGuild()` (включая Микро-ГЛ) и PL с обзором всей гильдии. Frontend скрывает маршрут от Микро-ГЛ, а backend-тест всё ещё ожидает для PL только собственную консту. Это не подтверждённая утечка — эти роли уже видят guild roster, — но drift повышает вероятность будущей ошибки авторизации.

Рекомендация: зафиксировать один продуктовый контракт, вынести проверку scope в policy/service и покрыть одинаковыми backend/router tests.

### R1 · Высокий · backup не включает private media

`deploy/scripts/backup.sh` архивирует базу и `storage/app/public`, но пользовательские файлы медиаленты лежат в `storage/app/private/media`. При восстановлении текущего backup они будут потеряны, хотя записи останутся в БД.

Рекомендация: включить весь согласованный набор uploads (`public` и `private/media`), добавить checksum/manifest, шифрование off-site копии и автоматический restore test.

## Производительность

### P1 · Высокий при росте нагрузки · синхронные OCR/rembg

Один OCR-запрос выполняет несколько проходов Tesseract и полнопиксельные циклы PHP; один rembg-запрос может занимать до 90 секунд. Это самые дорогие операции и первая цель для изоляции в worker/queue. До выноса в очередь нужны жёсткие dimension limits, отдельный пул и метрики времени/памяти.

### P2 · Средний · статические ресурсы frontend

Production build успешен. Главный JS — 329.68 kB (114.58 kB gzip), главный CSS — 226.35 kB (45.29 kB gzip). Маршруты уже разбиты на lazy chunks, но стартовый bundle включает i18n и 16 font imports. Сборка содержит 32 font-файла общим размером 527.84 kB.

Каталог `public/images` содержит около 30.9 MB. Самые заметные файлы: favicon 3.67 MB, два background PNG 3.42/2.68 MB и profile assets до 2.37 MB каждый. Не все они загружаются на старте, однако отдельные страницы передают существенно больше байтов, чем требуется для экранных размеров.

Рекомендации:

1. Пересобрать favicon в 16/32/48 px и добавить компактный ICO/PNG.
2. Конвертировать крупные PNG в WebP/AVIF, задать responsive variants и реальные `width`/`height`.
3. Оставить только используемые веса/форматы шрифтов или применить variable fonts и unicode subsets.
4. Разделить накопленный `style.css` по страницам и удалять дубли после coverage-проверки.
5. Установить budgets в CI: стартовый JS ≤ 130 kB gzip, CSS ≤ 60 kB gzip, route image ≤ 500 kB.

### P3 · Средний при росте данных · отчёты и wildcard search

Readiness и attendance загружают выбранных игроков/активности целиком и считают серии/дельты в PHP. Это приемлемо для небольшой гильдии, но время и память растут примерно как произведение игроков и активностей. Поиск `ILIKE '%...%'` в игроках, media и audit log не использует обычный B-tree; popular media сортируется коррелированным `COUNT`.

Рекомендации:

- включить `pg_trgm` и GIN trigram indexes для реально используемых search-полей;
- кэшировать/предагрегировать посещаемость и популярность media при подтверждённом росте данных;
- ограничить максимальный период экспортов и выполнять XLSX через очередь при больших выборках;
- добавить query-time и memory метрики, затем снимать `EXPLAIN (ANALYZE, BUFFERS)` на production-подобном dataset.

### Что уже оптимизировано

- dashboard строит 14-дневную динамику двумя пакетными выборками, а не запросом на каждый день;
- payout/reconciliation покрыты тестами на отсутствие N+1;
- коллекции игроков и выплат пагинируются;
- private media в production отдаёт Nginx после проверки Laravel;
- маршруты Vue загружаются динамически;
- существуют составные индексы для основных статусных и финансовых выборок.
