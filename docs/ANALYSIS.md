# Анализ реализации и продуктовые решения

Актуализировано 2026-09-10. `PROJECT.md` содержит исходное задание; фактические контракты описаны в `API.md`, `PERMISSIONS.md` и коде. Технические риски вынесены в [`TECHNICAL_AUDIT.md`](TECHNICAL_AUDIT.md).

## Неизменённые инварианты

- игрок получает долю только при наличии в `activity_players`;
- базовая доля рассчитывается целочисленно, остаток не распределяется;
- индивидуальный и общий коэффициенты прайма фиксируются в snapshot начисления;
- оценка лута не создаёт золото, а выплата списывается только из золотого ledger;
- золото и доступный остаток предметов не могут стать отрицательными;
- attendance уникален в пределах события;
- paid earnings и завершённые финансовые snapshots не редактируются;
- аукцион и выплата не могут быть завершены дважды;
- курс жетона фиксируется при старте аукциона или token-based distribution.

## Реализованные решения

1. В справочнике и статистике остаются только праймы; legacy mini-activity записи поддерживаются для совместимости миграций.
2. Pending начисления можно отменить, исправить активность и пересчитать; связанные с payout или paid начисления заблокированы.
3. Payout создаётся по периоду или явному списку активностей. Возможен proportional split заданного количества золота/жетонов.
4. Недостаток золота проверяется атомарно при фактической оплате.
5. Лот резервируется при старте. Аукцион без ставок освобождает резерв; proxy bidding определяет единственного победителя; ставка около deadline продлевает аукцион.
6. Завершение аукциона подтверждает получение эквивалента золота; отдельный баланс игрока не моделируется.
7. Player по умолчанию деактивируется логически. Permanent delete разрешён только без user link и истории.
8. Новый Discord user создаёт заявку на существующего или нового персонажа; подтверждение выполняет администратор либо PL целевой консты.
9. Новый пользователь имеет роль member до явного назначения дополнительных ролей.
10. Пользователь видит собственные выплаты; финансовые команды доступны только ГЛ и Разработчику.

## Открытые продуктовые решения

1. **Readiness для руководителей.** Backend даёт Микро-ГЛ доступ и PL обзор всей гильдии; frontend скрывает страницу от Микро-ГЛ, старый тест ограничивает PL собственной констой. Нужен единый контракт.
2. **Срок remembered-сессии.** Вход сейчас всегда выполняется с `remember=true`; срок и отзыв устройств не определены.
3. **Внешние direct media.** Нужен выбор между любым HTTPS URL, allowlist платформ и защищённым proxy.
4. **Масштаб отчётов.** Не определены максимальный период/размер XLSX и момент перехода на async export.
5. **Retention файлов.** Нужно согласовать срок хранения private media, OCR temp и character renders вместе с backup policy.
